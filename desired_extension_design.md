# Desired Extension Design — User-Centric Job Application Auto-fill

# Extension name: QuickFill

This document is a self-contained specification for an auto-fill Chrome extension to help
users apply to jobs quickly, easily, and without redundancies. 

It describes:

- the philosophy of the extension,
- the data model,
- every workflow,
- the architectural pieces that need to exist,
- the UX of the side panel and options pages,
- the security and storage model,
- the LLM-backend abstraction,
- the logging story.


v1 officially supports English-language forms and values only. Non-English pages may work opportunistically but are not guaranteed. 

---

## 1. Philosophy

The extension is **user-centric**, not page-centric:

- It does **not** scan or auto-detect application pages.
- It does **not** auto-fire on focus.
- It does **not** automatically submit anything.
- It is initiated **only** when the user has a field in focus (fallback: the cursor is over an element) and presses
  `Alt+A`.
- All data is stored locally and encrypted behind a master password. The only
  non-local network traffic is the LLM round-trip when the user has chosen 
  a cloud backend, or the one-time download/update of the local embedding model.
- Power-user knobs are exposed: every prompt template is editable; the LLM
  backend is swappable between Anthropic / Google Gemini / OpenAI / a local
  Ollama server; logging is toggleable for debugging.

## 2. Data model

The four persistent stores — Profile (§2.1), Answer history (§2.2),
Story list (§2.3), and Settings (§2.4) — are each encrypted on disk under
the master-password-derived key, and each is exportable + importable via
the Backup workflow (§8.3).

Active application (§2.5) is the one runtime piece of cross-fill state
that is **not** persisted: it lives in `chrome.storage.session`, is cleared
when the browser closes, and is excluded from backups.

### 2.1 Profile

A dictionary of canonical keys → one or more values, plus an alias map so
multiple labels can resolve to the same canonical key.

```ts
type ProfileValue = {
  id: string;                 // canonical key, e.g. 'last name' (normalized as below for aliases).
                              // Always equal to the key under which this value is stored in
                              // Profile.canonicalData — kept on the value for self-describing logs / exports.
  values: string[];           // a key may have several values
  defaultValueIndex: number;      // the index of the value that is to be treated as the default value. Initially set to 0, and can be changed in the Profile management UI in settings.
  updatedAt: number;
};

type Profile = {
  // alias label → canonical key. Both alias keys and canonical keys are normalized
  // identically at write time:
  //   NFKC, lowercase, delete every non-alphanumeric non-whitespace char, trim, collapse whitespace.
  // The map always includes the identity entry "K → K" for every canonical key K, so a single
  // lookup always resolves a (cleaned) label to its canonical key when one exists.
  aliasMap: Record<string, string>;
  canonicalData: Record<string, ProfileValue>;
  sensitiveKeys: string[];   // canonical keys flagged as sensitive (excluded from cloud-LLM prompts by default).
};
```

Initialized at onboarding from a user-uploaded resume (LLM-parsed). Editable
at any time on the Options → Profile page (add/remove canonical keys, edit
values, set default value, manage aliases, mark/unmark sensitive).

### 2.2 Answer history

The conceptual key for each entry is the tuple `(question, generic
description of company+role, timestamp)`. Entries are retrieved later by
**semantic similarity** over the question and the description (see §6 RAG).

```ts
type AnswerHistoryEntry = {
  id: string;                       // uuid

  // Collected from the user when they initiate the extension to auto-fill a question 
  // that requires generation.
  companyName: string;
  role: string;
  userBlurb: string | null;         // optional user-supplied notes about company

  // Derived at the initial use, reused until a change in the above is made.
  // Generated by the LLM ("genericKey" = company-name-free description of
  // industry+stage+role) and embedded so we can do semantic match on it.
  genericKey: string;
  genericKeyEmbedding: number[];

  // Per-entry.
  question: string;                 // the field's resolved question text
  questionEmbedding: number[];        // embedding of question
  answer: string;                   // the user-confirmed answer

  createdAt: number;
  updatedAt: number;                // time of most recent update (updates happen to avoid redundancy)
};
```

`companyName`, `role`, and `userBlurb` are recorded for human readability and
auditing on the Answer history options page. They are **not** part of the RAG
key — semantic search runs over the question text and the generic
description, never the company name. This is intentional: the goal is to
reuse "I led a project that…" answers across applications regardless of
which company they were originally written for. A core benefit is for apps to
similar companies (e.g. consulting companies) where we can reuse the "angle"
given by the user in their answer.

### 2.3 Story list

A list of STAR-method (Situation, Task, Action, Result) stories the user has
captured, each tagged with LLM-extracted keywords describing what aspect of
the candidate they showcase ("learning", "leadership", "shipping under a
deadline", "mentorship", etc.).

```ts
type Story = {
  id: string;
  content: string;             // the STAR narrative as one block
  keywords: string[];          // LLM-extracted tags (or user-provided)
  createdAt: number;
  updatedAt: number;
};
```

Stories can be added by the user manually (Options → Stories), suggested by
the resume parser at onboarding, or proposed automatically after a save of an edited 
generated answer when the LLM detects a reusable narrative in the user's confirmed 
answer (see §4.4 step 6, story discovery).

### 2.4 Settings

A single `Settings` blob persisted as an encrypted entry under `chrome.storage.local`.
Every numeric knob below has a default in `shared/constants.ts → DEFAULT_SETTINGS` and
is editable on the Options pages (§10).

```ts
type Backend = 'anthropic' | 'openai' | 'gemini' | 'ollama';

type PromptTaskName =
  | 'classifier' | 'chooser' | 'answer_length' | 'story_answer_prompt'
  | 'resume_parse' | 'story_discovery' | 'generic_key';

type Settings = {
  activeBackend: Backend;
  backends: {
    anthropic: { apiKey: string; model: string };
    openai:    { apiKey: string; model: string };
    gemini:    { apiKey: string; model: string };
    ollama:    { baseUrl: string; model: string };
  };
  // Empty / whitespace-only string == "use the default from
  // DEFAULT_PROMPT_TEMPLATES for this task" (resolved at render time;
  // never stored as a sentinel — see §7.3).
  prompts: Partial<Record<PromptTaskName, string>>;
  matching: {
    fuseThreshold: number;     // default 0.3 — used by §4.2 alias match and §4.5 add-to-profile.
  };
  rag: {
    historyGenericKeyWeight: number; // default 0.3 ('w' in §4.4 step 2).
    minTokens: number;               // floor for retrieval token budget.
    contextPercent: number;          // % of model context window allocated to retrieval.
  };
  dedup: {
    questionSimilarityThreshold:    number; // default 0.85 (§4.4 step 5).
    genericKeySimilarityThreshold:  number; // default 0.75 (§4.4 step 5).
  };
  logging: {
    enabled:     boolean;            // master switch for §11.
    logPayloads: boolean;            // gate the `payload` field on log entries.
  };
  // Override `getContextWindow(modelId)` for custom Ollama models (§6.3).
  customContextWindows: Record<string, number>;
};
```

### 2.5 Active application (session-only)

The user's currently-targeted application. Lives in `chrome.storage.session`,
not in any encrypted blob: it is short-lived (cleared on browser close) and
holds no values that aren't already derivable from user input + an LLM call.

```ts
type ActiveApplication = {
  companyName: string;
  role: string;
  userBlurb: string | null;
  genericKey: string;
  genericKeyEmbedding: number[];
  setAt: number;                  // when the user last submitted ApplicationSetup
};
```

When a `story_answer` fill begins and there is no `ActiveApplication`, the side
panel collects (companyName, role, userBlurb) from the user and the SW derives
`genericKey` + embedding (§4.4 step 1). The result is cached here so subsequent
fills in the same session don't re-prompt. The user can clear or replace it
from the active-application badge in the side panel header.

## 3. Architecture overview

Six runtime contexts, each with a single responsibility. The Background SW
is the hub; every arrow below terminates at it.

```
┌────────────────────┐                       ┌─────────────────────────┐                       ┌─────────────────┐
│ Content script     │◀── port (fill-       │ Background SW           │── port (fill-       ──▶│ Side panel      │
│ (every <all_urls>  │     session) ───────▶│ (singleton orchestrator,│      session) ─────────│ (Svelte)        │
│  frame; passive    │                      │  storage, LLM, RAG,     │                        │                 │
│  until first Alt+A)│                      │  logger)                │                        │                 │
└────────────────────┘                      └────────────┬────────────┘                        └─────────────────┘
                                                         │ rpc (sendMessage)
                                  ┌──────────────────────┼──────────────────────┐
                                  ▼                      ▼                      ▼
                         ┌─────────────┐         ┌─────────────┐        ┌──────────────────┐
                         │ Options     │         │ Onboarding  │        │ Offscreen doc    │
                         │ (Svelte)    │         │ (Svelte)    │        │ (Transformers.js │
                         │             │         │             │        │  for embeddings) │
                         └─────────────┘         └─────────────┘        └──────────────────┘
```

The side panel also opens RPC channels for non-session reads/writes (settings,
profile, etc.) — only the live fill flow goes over the port.

### 3.1 Single rule: no business logic in the content script

The content script knows the DOM. It does not know about profiles, stories,
LLMs, or storage. It exposes:

- A way to find the question text near a focused element ("tree climbing" —
  see §4.1).
- A way to capture/commit a value on a form element.
- A manual-highlight fallback when tree climbing fails.
- An Esc handler that posts an "abort" event.

All content scripts must be compiled as IIFEs (Immediately Invoked Function Expressions) 
or ES modules to avoid polluting the host page's global window scope. (Vite handles this 
by default, but developers must not explicitly attach state to window).

### 3.2 Single rule: the SW is the only writer

All persistent state, LLM calls, and embedding calls live in the SW. The
side panel, options, and onboarding only ever read or send commands; they
never write to `chrome.storage` directly.

### 3.3 Single orchestrator instance

One `FillSession` object in the SW owns the active fill. There is at most
one active session at a time. Starting a new session aborts any in-flight
LLM stream from the previous one.

### 3.4 Message protocol

Two channels:

1. **RPC** — one-shot request/response (`chrome.runtime.sendMessage`). Each
   op declares request and response zod schemas; both sides validate.
   Errors are surfaced as a discriminated `{ ok: false, kind, message }`
   union, never thrown across contexts. Used for: onboarding, settings,
   profile/stories/history reads + writes, backups, diagnostics.
2. **Port** — long-lived bidirectional (`chrome.runtime.connect`) named
   `fill-session`. The content script and the side panel each open one. All
   events on the port are validated against a single discriminated union
   keyed by `t`. Used for: detective, manual-highlight, fill-plan, LLM
   token streams, status / error / setup-needed broadcasts, commit / revert
   / abort.

Implementation note: keep the protocol in `src/background/messaging.ts` and
import it from every context. The validator wrapper that swallows
disconnect-during-post errors (Chrome bfcache, SW restart) is critical —
without it the panel will throw on routine page navigations.

**Port discrimination.** Because both the content script and the side panel
connect under the same port name `"fill-session"`, the SW must distinguish
them in `chrome.runtime.onConnect`. Use `port.sender?.tab != null` as the
discriminator: content script ports always have `sender.tab` set; side panel
ports do not. Assign each to a typed wrapper immediately on connect
(`ContentPort` vs `PanelPort`) and reject (disconnect) any port that matches
neither.

## 4. The fill workflow (the core path)

All steps below are kicked off **only** by the user pressing `Alt+A` while
a form field has focus (or as a fallback if no element is in focus: the 
element that the cursor points to, if it is of appropriate type, see 
below; if this also fails, the user is shown an error in the side panel). 
There is no auto-detect.

The user can press `Esc` at any moment from `Alt+A` until the field value 
is committed, which aborts the session, and cancels any in-flight LLM stream.

The Alt+A shortcut is registered in the manifest under commands. The
Background SW listens to `chrome.commands.onCommand`. When `trigger-fill`
fires, Chrome passes the active `Tab` as the second argument to the command
listener (Chrome 114+); use `tab.id` directly. For robustness, also handle
the case where `tab` is undefined by falling back to
`chrome.tabs.query({ active: true, currentWindow: true })`. The SW messages the content script to run the detective **first**, then calls
`chrome.sidePanel.open({ tabId: tab.id })`. This ordering is important:
`chrome.sidePanel.open()` may move focus away from the page in some Chrome
versions, so the detective must be dispatched before the panel opens to avoid
a race where `document.activeElement` has already changed by the time the
content script reads it.

### 4.1 Tree climbing — find the question text

Run in the content script, on the focused element. Returns a `string` or
`null`. **The very first line of the `run-detective` handler must synchronously
read and store `document.activeElement` before any `await` or async work.**
This guarantees the reference is captured before `chrome.sidePanel.open()`
(dispatched immediately after by the SW) can move focus away from the page.
All subsequent tree-climbing and analysis runs against this stored reference,
never a re-read of `document.activeElement`.

Try in this priority order, first non-empty wins:

1. `aria-labelledby` — resolve the space-separated id list, join the
   trimmed innerText of each.
2. `aria-label`.
3. Closest ancestor `<label>` (shadow-DOM aware: if you reach the top of an
   open `ShadowRoot` without matching, hop to its host and continue). 
4. Up to 3 preceding siblings: take the first non-empty line of innerText.
5. Up to 5 ancestor levels: check `data-label`, `data-question`,
   `data-field-label`, `data-testid` attributes (cap at 200 chars), and any
   direct child `<legend>`, `<label>`, `<h1>..<h6>`.
6. Give up → `null`.

When tree climbing returns `null`, the side panel asks the user to highlight
the question text on the page and press `Enter` to capture it (a tooltip 
sticky to the mouse cursor should appear until Enter or Esc are pressed). 
The  captured text is then used as the question text and the workflow resumes 
from §4.2. The state where the extension is waiting for a question/label text 
to be selected should be indicated clearly in the side panel. 

Workflow for manual highlight:
1.  Enter manual label capture mode in the active frame only
2.  Show tooltip near pointer
3.  On mouseup or selectionchange, read window.getSelection()?.toString()
    and show current selection in side panel.
4.  Normalize whitespace; reject empty selections (by showing a warning in the side panel)
5.  On Enter, submit current non-empty selection
6.  On Esc, cancel
7.  Register listeners in capture phase and suppress only extension-owned handlers
8.  Time out after 1 minute of inactivity

The detective also captures, alongside the label:

- `pageContext`: `document.title`, `location.hostname`, `og:site_name`
  meta if present, the page's first `<h1>` if present. Used to pre-fill
  the ApplicationSetup form's company-name field as a suggestion (the user
  can override).
- `fieldType`: one of `text | email | tel | url | number | date | password
  | textarea | select | radio | checkbox | contenteditable | unknown`.
- `options`: for `<select>` and radio groups, the option labels.
  Radio groups are identified by shared `name` attribute within the
  containing form; option labels are taken from the associated `<label>`
  or the radio's `value` if no label exists.
- `currentValue`: the field's value at capture time (used by the
  add-to-profile flow and to display previous-value diffs).
- An opaque `elementRef` (uuid) so the SW can ask the content script to
  commit/revert against the same element later. The content script keeps a
  `Map<uuid, WeakRef<Element>>` so detached nodes can still be GC'd.

Together these form the `FillPlan` returned to the SW:

```ts
type FillPlan = {
  question: string | null;        // null when tree-climbing fails — manual highlight requested.
  fieldType:
    | 'text' | 'email' | 'tel' | 'url' | 'number' | 'date'
    | 'password' | 'textarea' | 'select' | 'radio'
    | 'checkbox' | 'contenteditable' | 'unknown';
  options: string[] | null;       // null unless fieldType is 'select' or 'radio'.
  currentValue: string;
  pageContext: {
    title: string;
    hostname: string;
    siteName: string | null;     // og:site_name
    h1: string | null;
  };
  elementRef: string;             // uuid; valid only within (tabId, frameId).
  tabId: number;
  frameId: number;
};
```

Disabled / readonly fields and `<input type="file">` are rejected at detective
time — the side panel surfaces "This field can't be filled" and ends the
session immediately.

Iframe handling: with `all_frames: true`, the focused field can live in any
frame. The frame whose content script captured the focus event owns the
session, and `(tabId, frameId, elementRef)` identifies the element for
commit / revert. Only the top-level tab's side panel is shown; cross-frame
coordination is the SW's responsibility.

### 4.2 Direct-match check against the profile

After the question text is known, the SW:

1. Normalize the label using the **shared cleaning recipe** (NFKC, lowercase,
   delete anything that is not alphanumeric or whitespace, collapse whitespace,
   trim). This is the same recipe used everywhere a label is normalized — see
   §6.2 for why the shared helper is critical.
2. Run a fuzzy search against `profile.aliasMap` using fuse.js with threshold
   `settings.matching.fuseThreshold` (default 0.3, editable on Options → General).
   Resolve the matched alias to its canonical key.

If the match succeeds:

- Take the default value for the canonical key for `text | email | tel
  | url | number | date | password | textarea | contenteditable | unknown`
  field types.
- For `select` / `radio` fields, run a fuzzy search via fuse.js (same
  threshold) for every stored value of the canonical key against the
  available options. If no value matches, pass the canonical key, the stored
  values, and the available options to the LLM (one-shot, non-streaming) via
  the `chooser` prompt — it returns either the nearest option label or the
  exact string `"No good options"`. On `"No good options"`, the match is
  treated as if it never happened and the workflow falls through to §4.3.
  The chooser prompt template is editable in Options → Prompts; the default
  lives in `shared/constants.ts → DEFAULT_PROMPT_TEMPLATES.chooser`.
- For `checkbox` fields, interpret the canonical key's default value as a
  boolean: treat `"yes"`, `"true"`, `"1"`, and `"checked"` (case-insensitive)
  as checked; everything else as unchecked. No fuzzy search or chooser prompt
  is needed. Commit sets `element.checked` accordingly.
- The SW posts `commit` over the port; the content script writes the value via the
  native setter (so React / Vue can't clobber it) and dispatches `input` +
  `change` events. 
  (Implementation note for the native setter): Do not assign element.value directly. 
  To bypass React/Vue state tracking, you must capture the native prototype setter. 
  Here is some general guidance:
  * text/email/tel/url/number/date/password: use native prototype value setter on HTMLInputElement
  * textarea: use native prototype value setter on HTMLTextAreaElement
  * select: set value, confirm selected option exists, dispatch input then change
  * checkbox: set checked, dispatch input then change
  * radio: find matching radio by value, set checked = true, dispatch input then change on the selected radio
  * contenteditable: clear the element, set `textContent` to the new value, then move the caret to the end using a `Range` (`element.appendChild(document.createTextNode(value)); range.selectNodeContents(element); range.collapse(false)`). Do not use `innerHTML` (XSS risk). Do not rely on the current selection state.
  * all commits: preserve focus if possible; if focus moves, restore it; emit bubbling events
  * all failures: return a typed error instead of partially writing
  Followed immediately by dispatching a new event.
  Note: if the selected element is not supported as above for setting a value, 
  the side panel shows “This field type is not supported yet, here is the answer:”
  with the answer value and a "copy" button that copies it to clipboard. This way
  the user can input it by hand if needed.
- Show the committed retrieved value in the side panel (as part of a history of recent
  fills and saves). Also in the side panel, the user can switch to a different stored 
  value for the canonical key, if such a value exists.

### 4.3 LLM classifier — what kind of field is this?

If the direct match fails, the SW asks the LLM to classify the field. The
classifier sees:

- the field label/question,
- the field type (`textarea`, `text`, etc.),
- the available options (for selects/radios),
- the list of canonical profile keys,

The classifier returns one of three categories:

1. **`profile_existing_value`** — this is a basic personal data point that
   exists in the stored profile (that fuzzy matching above failed to catch).
   The LLM returns both the category and the `canonicalKey` it matched.
   The SW looks up `profile.canonicalData[canonicalKey]` and proceeds from
   the "if the match succeeds" bullet in §4.2 onward. 
   No second fuzzy pass is run.

2. **`profile_update`** — this looks like a basic personal data point that's
   missing from the profile (e.g. "middle name", "preferred pronouns",
   "LinkedIn URL"). The LLM also returns a suggested canonical key. The
   side panel displays a card asking the user: "We don't have this in your
   profile. Add it?" with an editable label / value pair. On confirm, the
   value is saved into the profile under the suggested key (the user can
   edit the key) and **also** committed to the field. If the field type is 
   a multi-choice (e.g. radio, select, etc.), the user selects a value from
   the given options rather than writes it from scratch.

3. **`story_answer`** — this is a narrative or experiential question that
   needs LLM generation ("Tell us
   about a time…", "Why this company?", "Describe your approach to X"). Go
   to §4.4.

The classifier prompt template is editable on Options → Prompts. The
default lives in `shared/constants.ts → DEFAULT_PROMPT_TEMPLATES.classifier`
and asks for strict JSON (choose the schema and be consistent with it).

### 4.4 LLM answer generation (story_answer path)

When the classifier says `story_answer`:

1. **Application context check.** The answer generator needs the active
   application's `genericKey` (and its embedding) to bias retrieval. If no
   active application is set in this browsing session, the side panel
   prompts the user for:
   - Company name (required)
   - Role title (required)
   - Short blurb describing the company (optional)

   On submit, the SW renders the `generic_key` prompt with these three
   inputs, runs it via the active LLM (non-streaming, single-shot), parses
   strict JSON, and embeds the resulting `genericKey` string. The result is
   cached as the session's `ActiveApplication` in `chrome.storage.session`
   (RAM-only; gone when the browser closes) so subsequent fills in the
   same application don't re-prompt.

2. **RAG retrieval.** The SW:
   - Embeds `question`.
   - Scores each `AnswerHistoryEntry` by
     `(1 - w) * cosine(question, entry.questionEmbedding)
      +        w * cosine(genericKey, entry.genericKeyEmbedding)` where
     `w = settings.rag.historyGenericKeyWeight` (default 0.3). The
     genericKey component preferentially surfaces past answers written for
     applications that look like the current one without hard-filtering.
   - Computes a token budget: `max(settings.rag.minTokens,
     floor(modelContextWindow * settings.rag.contextPercent / 100))`.
   - Greedy-packs the scored list into the token budget (see §6.3): sort
     entries by combined score descending; iterate in that order; add each
     entry whose estimated token count fits within the remaining budget;
     **skip** (do not stop) entries that don't fit and continue to the end
     of the list. This prevents a single high-scored but large entry from
     starving the rest of the budget.

3. **Prompt rendering.** Render `story_answer_prompt`
   with these variables:
   - `active_application` — formatted summary (company, role, generic key,
     optional notes blurb).
   - `stories` — the **full story list** (always sent in full; see §7.4).
   - `history` — the **retrieved** subset of past answers (top-K under
     budget).
   - `profile` — concise list of non-sensitive canonical values, formatted
     as `- key: value` lines.
   - `field_label`.
   - `max_length` — determined as follows: if the DOM element has a non-zero
     `maxlength` attribute, use that integer directly (no LLM call).
     Otherwise, run the `answer_length` prompt (one-shot, §7.3) with the
     field label and field type to estimate a sensible character budget.

   Sensitive profile fields (anything in `profile.sensitiveKeys`) must be
   excluded from `profile` — never sent to a cloud LLM unless the
   user explicitly requests it for a specific fill.

4. **Streaming.** The SW streams tokens via the active backend's adapter
   and forwards each token as a `stream-token` event to:
   - the side panel (renders into the draft area with a blinking caret),

   The user can:
   - Press `Esc` → SW aborts the LLM stream, tears down side panel
     state, ends session.
   - Press `Enter` (when streaming is done) or click "Approve & fill" →
     commit the current draft.
   - Click "Edit" → hand-edit the draft in a textarea in the side panel before committing.
   - Click "Cancel" → same as `Esc`.

   **Mid-stream failure.** If the adapter yields a `{ kind: 'error' }` chunk
   (network drop, 5xx, 429, auth, etc.), the SW does NOT auto-retry. It:
   - keeps whatever tokens have already streamed visible in the side panel
     draft area,
   - surfaces the error in `ErrorBanner.svelte`,
   - shows a **Retry** button when `retryable === true` (§7.1) — Retry
     re-runs the same prompt with identical RAG retrieval and active
     application; the previously-streamed partial draft is discarded,
   - on `retryable === false`, only Edit / Cancel remain (the user can
     edit the partial draft into something usable, or abort).

5. **Commit + history insert + dedup.** When the user confirms:
   - The content script writes the value to the field via the native setter (as for direct matches).
     The form already has the new answer at this point — nothing the SW does
     in the steps below changes that.
     We repeat the note from the direct match value setting: 
     Note: if the selected element is not supported as above for setting a value, 
      the side panel shows “This field type is not supported yet, here is the answer:”
      with the answer value and a "copy" button that copies it to clipboard. This way
      the user can input it by hand if needed.

   - The SW embeds (the cleaned) `question` to produce `questionEmbedding`.
   - The SW runs the dedup check against existing history entries. **Only
     entries whose embedding length matches the current model's dimension
     are eligible** (e.g. 384 for the default `Xenova/all-MiniLM-L6-v2`).
     Entries embedded under a different model are skipped and treated as
     non-duplicates — see §6.1 for the embedding-model commitment.
     For each eligible entry:
     - Compute `qSim = cosine(newQuestionEmbedding, entry.questionEmbedding)`
       and `gSim = cosine(activeGenericKeyEmbedding, entry.genericKeyEmbedding)`.
     - The entry is a duplicate iff
       `qSim ≥ settings.dedup.questionSimilarityThreshold` (default 0.85)
       **and** `gSim ≥ settings.dedup.genericKeySimilarityThreshold` (default 0.75).
     - Among duplicates, pick the best by combined score
       `0.7 * qSim + 0.3 * gSim` and **merge into** it: keep its `id` and
       `createdAt`; set `updatedAt = now`; overwrite `companyName`, `role`,
       `userBlurb`, `answer`, `question`, `genericKey`, and both embeddings
       with the new values.
     - If no entry is a duplicate, insert a new entry with a fresh uuid.
   - If a merge happened, the side panel shows a "Merged into an older,
     more general answer. Keep the older one instead?" toast for 10s with
     an Undo button.

   **Merge undo.** Clicking Undo restores the older history entry to its
   pre-merge state (every overwritten field reverts). The form field is
   **not** touched — the user already received the answer they wanted for
   this question; only the persisted history changes. The new answer
   produced this turn is discarded from history (it is not stored as a
   separate entry). The use case: the new answer was tightly specific to
   this application, while the older entry was a more general formulation
   that is more useful to keep around for future RAG retrieval.

6. **Story discovery.** If the user **edited** the LLM-generated answer
   before confirming, the SW asks the LLM whether the edited answer
   contains a new reusable story not already represented in the existing
   stories (based on content). Render the `story_discovery` prompt with:
   - active application summary,
   - the question,
   - the edited answer,
   - the existing story list.

   If the LLM proposes a story, the side panel shows a "save as story?"
   toast with the proposed content + keywords, editable. On confirm, append
   the new story to the story list.

   This is fire-and-forget — it does not block the commit. If the user
   did not edit the answer (just hit Enter or Approve on the LLM's
   unmodified draft), skip this step entirely: the original draft was
   built from the existing story list, so there's no new narrative to
   discover.

### 4.5 Add-to-profile flow (Alt+S)

`Alt+S` is the user telling the extension "save the value
currently in this focused field to the profile". The SW
runs the detective on the focused field, then:
  - If `currentValue` is empty or whitespace-only, abort with a status:
    "Nothing to save — the field is empty." No write happens.
  - If `question` is `null` (tree-climbing failed), the side panel runs the
    same manual-highlight flow as §4.1 to capture the label before saving.
  - If the cleaned label fuzzy-matches an entry in `profile.aliasMap` via
    fuse.js using the same threshold as §4.2 (`settings.matching.fuseThreshold`),
    append `currentValue` to the matched canonical key's `values` (deduped
    case-insensitively).
  - Otherwise create a new canonical key from the cleaned label, add the
    identity entry to `aliasMap`, and store `currentValue` as the first value.
  - **Confirmation gate.** If the cleaned label is longer than 50 chars or
    `currentValue` is longer than 100 chars, the side panel shows a confirmation
    card with the proposed key + value (both editable) before the write. The
    user can also flip the "mark as sensitive" checkbox here.
  - The write is logged to the side panel status: "Saved to profile under `<key>`."
    A delete button is available next to it to delete the saved value if the user
    desires. If there was an old value in the field, the delete button should revert
    to that rather than completely erase it. 

### 4.6 Esc behavior — global, every state

Two `keydown: Escape` listeners cooperate to cover every active surface:

1. **Content script** — a capture-phase `keydown: Escape` listener posts an
   `abort` event over the port whenever a session is active. This catches Esc
   when the user's focus is on the page.
2. **Side panel** — the side panel registers its own `keydown: Escape` handler
   (on `window`, capture phase) that posts the same `abort` RPC when a session
   is active. This catches Esc when the user's focus is inside the side panel
   (e.g., while editing the draft in `DraftArea`).

In both cases, the SW:

- aborts any in-flight LLM stream,
- broadcasts `close` to the side panel (which clears its draft, status,
  setup form, and toasts),
- broadcasts `close` to the active-frame content script (which removes 
  the manual-highlight tooltip if present, andclears its `currentTarget`),
- discards the in-flight `Session`,
- emits a status to the side panel: "Cancelled."

The side panel "Cancel" button does the same thing by posting the same
`abort`.

## 6. RAG and embeddings

### 6.1 Embedding model

- Local Transformers.js: `Xenova/all-MiniLM-L6-v2`, 384 dims. Mean-pooled,
  L2-normalized so cosine similarity = dot product.
- Lives in an **offscreen document** because MV3 service workers can't host
  the WASM bootstrap (no `document`, no Worker host APIs the
  onnxruntime-web init reaches for). The SW proxies embed requests over
  `chrome.runtime.sendMessage` to the offscreen document.
- Force `numThreads = 1` and `proxy = false` on the ORT WASM backend.
  Multi-threaded ORT requires `SharedArrayBuffer`, which requires
  cross-origin isolation (`COOP: same-origin` + `COEP: require-corp`) —
  extension pages don't get those headers in MV3, so any value > 1
  silently downgrades or fails. ORT's proxy mode runs the WASM session in a
  Worker spawned from a `blob:` URL, which the extension CSP (§13) blocks;
  inline execution on the offscreen document's main thread is fine for our
  short, infrequent calls.
- Loading the WASM relies on `'wasm-unsafe-eval'` being present in the
  extension `content_security_policy` (see §13). Without it, ORT cannot
  compile the model.
- **Embedding-model commitment.** Once the extension is in use, switching
  the embedding model invalidates every stored `*Embedding` field —
  similarities are not comparable across models, and dimensions may differ.
  Treat the model id as effectively pinned for the lifetime of an install;
  changing it would require a re-embed pass over all stories and history
  entries. The dedup logic at §4.4 step 5 explicitly skips entries whose
  embedding length doesn't match the current model's dimension as a
  safety net.
- Warm the model up opportunistically right after the user unlocks the
  vault, so the first real fill doesn't pay for the ~30 MB
  IndexedDB-cached download.
- Lifecycle Management: Offscreen documents are ephemeral in MV3. Before 
  sending an embed RPC, the background service worker must check if the 
  offscreen document exists using chrome.offscreen.hasDocument(). If false,
  the SW must dynamically recreate it using 
  chrome.offscreen.createDocument({ url: 'src/offscreen/index.html',
  reasons: ['WORKERS'], justification: 'Run ONNX WASM inference for text embedding via Transformers.js' })
  before sending the message. (`WORKERS` is the conventional reason for
  Transformers.js offscreen documents; even though proxy mode is disabled and
  no blob-Worker is spawned, this is the accepted declaration for ML-inference
  offscreen use in the Chrome extension ecosystem.)

### 6.2 Save-side / retrieve-side embedding parity

This is the critical correctness invariant:

- At **save time**, the SW embeds `cleaned(question)`, where `cleaned` is the
  shared cleaning recipe defined in §4.2 step 1 (NFKC, lowercase, drop
  every non-alphanumeric non-whitespace char, collapse whitespace, trim),
  and stores the result as the entry's `questionEmbedding`.
- At **retrieve time**, the SW embeds `cleaned(question)` for the *current*
  field question/label using the same recipe, then runs cosine against
  every eligible entry's `questionEmbedding`.

If the recipe changes, **change it in one shared helper** (`shared/clean.ts`
or similar) so save + retrieve cannot drift. A drift here is silent: it
won't throw, it'll just kill recall — past entries become essentially
invisible to retrieval and dedup.

### 6.3 Token estimation

A single heuristic across all backends is fine for budgeting:
`Math.ceil(text.length / 3.5)`. This slightly overcounts vs. cl100k-base
and Anthropic's tokenizer — intentional, since the number is used to
size a *budget* and we'd rather under-pack than overflow the context
window. Make the helper accept a backend parameter so per-provider
tokenizers can be swapped in later (`gpt-tokenizer` is already a
dependency for OpenAI).

`getContextWindow(modelId)` looks up a model→tokens table; fall back to
8192 for unknown models. Allow the user to override the context window for
custom Ollama models in Settings.

## 7. LLM backends

### 7.1 Provider-agnostic surface

Every adapter implements:

```ts
type ChatRequest = {
  messages: { role: 'system' | 'user' | 'assistant'; content: string }[];
  systemPrompt?: string;
  maxTokens?: number;
  temperature?: number;
  signal?: AbortSignal;     // for Esc 
};

type StreamChunk =
  | { kind: 'token'; text: string }
  | { kind: 'done';  fullText: string }
  | { kind: 'error'; message: string; retryable: boolean };

type Adapter = (req: ChatRequest, config: BackendConfig[Backend])
  => AsyncGenerator<StreamChunk, void, void>;
```

The orchestrator (`streamWith(backend, request, settings)`) picks the
adapter by `settings.activeBackend`. There is also a `complete` helper
that drains a stream into a single `{ ok, text }` for callers that only
need the final text (classifier, generic-key, story discovery, resume
parse).

`retryable` is the adapter's intent signal:
- `true` for network failures, 5xx, 429.
- `false` for auth errors, 4xx, user-aborted, structured "blocked"
  responses.

### 7.2 The four adapters

- **Ollama** — `POST {baseUrl}/api/chat`, JSONL stream. System message
  prepended as a normal chat turn. The user must run
  `OLLAMA_ORIGINS=chrome-extension://<id> ollama serve` to allow the
  extension origin (CORS). The Models options page must show this
  command pre-filled with the user's actual extension id.
- **Anthropic** — `POST https://api.anthropic.com/v1/messages` with
  `anthropic-version: 2023-06-01` and the
  `anthropic-dangerous-direct-browser-access: true` header (required to
  call from a browser origin). SSE; consume `content_block_delta` and
  `message_stop`. System prompt is the top-level `system` field.
- **OpenAI** — `POST https://api.openai.com/v1/chat/completions` with
  `Authorization: Bearer <key>`. SSE; consume `choices[0].delta.content`
  and `finish_reason`.
- **Gemini** — `POST .../v1beta/models/{model}:streamGenerateContent
  ?alt=sse&key={key}`. Map `assistant` → `model`; system text goes to
  `systemInstruction.parts[0].text`. Consume
  `candidates[0].content.parts[].text` and `finishReason`.

The orchestrator owns the abort semantics: pass `req.signal = abortController.signal`
through to each adapter's `fetch`; an Esc triggers
`abortController.abort()` and the generator returns silently.

### 7.3 Editable prompt templates

Every prompt template lives in `shared/constants.ts →
DEFAULT_PROMPT_TEMPLATES`. Settings carry per-task overrides. The
Options → Prompts page renders one textarea per task with:
- a "reset to default" button,
- a cheat-sheet of expected `{{snake_case}}` variables,
- a "customized" badge if the user has overridden the default.

Empty / whitespace-only override = "use default" (resolved at render
time, not stored as a special sentinel).

The prompt tasks are at minimum (mode = how the orchestrator runs the prompt):

| Task                  | Mode      | Returns           | Used in   |
|-----------------------|-----------|-------------------|-----------|
| `classifier`          | one-shot  | strict JSON: `{ category: 'profile_existing_value', canonicalKey: string }` \| `{ category: 'profile_update', canonicalKey: string }` \| `{ category: 'story_answer' }` | §4.3 |
| `chooser`             | one-shot  | a single option label from the provided list, or the literal string `"No good options"` | §4.2 |
| `answer_length`       | one-shot  | a positive integer (max characters)         | §4.4 step 3 |
| `story_answer_prompt` | streaming | free-text answer, ≤ `max_length` chars      | §4.4 step 4 |
| `resume_parse`        | one-shot  | strict JSON: extracted profile fields + suggested stories | §9 step 5 |
| `story_discovery`     | one-shot  | strict JSON: `{ proposeStory: boolean; content?: string; keywords?: string[] }` | §4.4 step 6 |
| `generic_key`         | one-shot  | strict JSON: `{ genericKey: string }`        | §4.4 step 1 |

"One-shot" prompts go through the orchestrator's `complete` helper (§7.1),
which drains the stream and returns `{ ok, text }`. Only `story_answer_prompt`
is rendered to the user as it streams.

Variable interpolation is `{{snake_case}}`, missing variables render as
`""`. JSON extraction from model responses must be lenient (strip code
fences, scan for the first balanced `{...}` or `[...]` while respecting
string literals, return null on failure).

### 7.4 One-shot LLM error handling

Any one-shot call (classifier, chooser, generic_key, answer_length,
story_discovery, resume_parse) that fails — network error, 5xx, 429, auth
failure, or JSON parse failure — is handled uniformly:

1. The SW surfaces the error in `ErrorBanner.svelte` with the error message.
2. The active session is **paused** (not aborted): the fill is not abandoned,
   and the side panel shows a **Retry** button.
3. Clicking **Retry** re-runs the exact same one-shot call with identical
   inputs; no new user input is required.
4. Clicking **Cancel** (or pressing Esc) aborts the session per §4.6.

The exception is `story_discovery` (§4.4 step 6), which is fire-and-forget:
its failure is logged but never surfaced to the user and never interrupts a
flow the user considers already complete.

### 7.5 What the LLM sees in the answer-generation step

At answer-generation time (`story_answer_prompt`, §4.4 step 3), the LLM gets:

- the full active application context (company, role, blurb, generic key),
- the **full** stored profile (excluding sensitive keys unless the user
  has opted in for this fill),
- the **full** story list,
- a **RAG-retrieved** subset of the answer history (top-K by combined
  question + generic-key similarity, packed under the token budget),
- the field label / question and max length for the answer.

The retrieval over answer history is required because the history can
grow unboundedly; the profile and story list are bounded enough that
sending them in full is fine.

## 8. Storage and security

### 8.1 What lives where

`chrome.storage.local` (persistent, encrypted blobs except `meta`):

- `meta` — plaintext: KDF parameters (PBKDF2-SHA256, 200,000 iterations,
  16-byte random salt) + the wrapped DEK + optional wrapped DEK under the
  recovery-phrase KEK. Plaintext is safe because the KEKs are derived from
  secrets that are never stored.
- `profile` — encrypted `Profile`.
- `stories` — encrypted `Story[]`.
- `history` — encrypted `AnswerHistoryEntry[]`.
- `settings` — encrypted `Settings`.
- `logs` — encrypted ring buffer of `LogEntry[]`, capped at ~2000 entries.

`chrome.storage.session` (RAM-only, cleared at browser close):

- The unwrapped DEK, exported as base64 — re-imported on SW restart so the
  user doesn't have to re-enter their password every time the SW is
  evicted.
- `activeApplication` — the per-session `ActiveApplication`.
- `isActive` / `activeTabId` flags.

### 8.2 Crypto

- DEK: random 256-bit AES-GCM key, generated during onboarding
      when the user first sets a master password.
- KEK: PBKDF2-SHA256, 200,000 iterations, 16-byte salt → AES-GCM key.
- Per-blob encryption: fresh 12-byte IV per write. AES-GCM auth tag is
  the wrong-password / tampering verifier (unwrap throws).
- Recovery phrase: 16 words from a 256-word list (8 bits per word ⇒ 128
  bits of entropy). Generated at onboarding, shown once. PBKDF2 the
  normalized phrase the same way as the password. Stored as a second
  wrapped copy of the same DEK on the meta blob.

If the user forgets both the password and the phrase, the data is
unrecoverable by design. There is no server.

### 8.3 Backups

- Format: a portable JSON envelope `{ format: 'backup/v1', version,
  exportedAt, kdf: { algorithm: 'PBKDF2', hash: 'SHA-256', iterations,
  saltBase64 }, payload: { cipherTextBase64, ivBase64 } }`. The `format`
  string is the only thing checked to gate `unsupported-format` errors;
  the numeric `version` allows back-compat envelope changes within the
  same family.
- Encrypted under a **separate export password** the user picks at
  export time. Don't reuse the master password — the backup is meant to
  be portable across machines and a one-trip secret is the right
  ergonomics.
- The plaintext bundle holds `{ version, exportedAt, profile, stories,
  history, settings }`.
- Import modes:
  - **Replace all** — overwrite profile / settings / history; replace the
    full story list.
  - **Merge stories** — leave profile / settings / history alone; union
    incoming stories by id (skip ids that already exist locally; never
    overwrite local edits).
- Import errors must be discriminated: `parse-envelope`,
  `unsupported-format`, `version-newer`, `wrong-password` (collapse
  AES-GCM auth-tag failure and JSON parse failure into one user-facing
  message — same remediation), `parse-payload`, `storage-failed`.
- **Embedding dimension mismatch on import.** Imported `AnswerHistoryEntry`
  records may have been embedded with a different model than the one currently
  in use. After import, treat any history entry whose
  `questionEmbedding.length` or `genericKeyEmbedding.length` does not match
  the current model's output dimension as if it has no valid embedding: the
  dedup and RAG retrieval logic already skip such entries (§4.4 step 5 and
  §6.1). No re-embedding pass is required at import time; entries will be
  re-embedded naturally the next time the same question is answered and a
  new history entry is created.

### 8.4 Sensitive data and cloud LLMs

- `sensitiveKeys` on the Profile is the canonical list of keys whose
  values must never be sent to a cloud LLM by default. The
  `profile` rendering for `story_answer_prompt` excludes them. 
  The Resume parser auto-flags a hard list (phone, address, DOB, SSN, 
  etc. — see `SENSITIVE_CANONICAL_KEYS`) and the user can mark / unmark on the
  Profile page.
- The Backup → Export flow shows a clear warning when the user is about
  to export a file that contains sensitive values (it always does, since
  the bundle is the full profile). Export is encrypted, so this is just
  user education.

## 9. Onboarding

A wizard in a new tab opened on first install. Steps:

1. **Welcome** — set expectations.
2. **Master password** — The onboarding UI prompts for a master password
   (minimum 8 characters; no other constraints). On submit, the `setup-master`
   RPC derives the KEK, generates the DEK, stores `meta`, seeds
   `DEFAULT_SETTINGS`, and initializes an empty `Profile`. The RPC always
   generates and wraps a recovery phrase internally; whether to display it is
   decided in step 3.
3. **Recovery phrase** — show the 16-word phrase as a 4×4 grid. The user must
   tick "I wrote this down" to continue. Allow opt-out: if the user chooses
   not to record the phrase, the UI removes the wrapped recovery DEK from
   `meta` via a `remove-recovery-phrase` RPC and shows a strong warning that
   forgotten password = permanent data loss. Either way, step 3 always has a
   phrase to show because `setup-master` always generates one; opt-out is
   decided after the user has seen it.
4. **AI backend** — pick `activeBackend`, paste API key (or, for Ollama,
   confirm the server is reachable; show the `OLLAMA_ORIGINS` command
   pre-filled with the user's extension id).
5. **Resume upload** — file picker accepting `.docx` and `.txt` only (the
   onboarding screen states this explicitly: "DOCX or plain text. PDF is
   not supported — paste the text into a `.txt` file or upload the source
   `.docx` instead."). Extraction happens in the onboarding page itself
   (mammoth.js for `.docx`, UTF-8 decode for `.txt`) — onboarding is a
   regular extension page with `DOMParser`, which mammoth needs and the
   service worker lacks. The extracted text is then sent via the
   `parse-resume` RPC; the SW runs the `resume_parse` LLM prompt → JSON
   validation → folds the result into a `Profile`. Sensitive keys are
   auto-flagged from `SENSITIVE_CANONICAL_KEYS` (§8.4). The user can skip
   this step and add profile fields manually on the next screen. If the
   `parse-resume` RPC fails (LLM error, JSON parse failure, or network
   error), the onboarding UI shows an inline error with a **Retry** button
   to re-send the same extracted text, and a **Skip** link to bypass resume
   upload and proceed directly to step 6 (manual profile entry).
6. **Profile review** — editable list of extracted fields, with the raw
   extracted text in a collapsible panel so the user can audit what the
   LLM saw. The user accepts (or edits + accepts) and the profile is
   committed.
7. **First fill** — instructional screen ("Press Alt+A on a form field to
   start. Press Esc to cancel at any time.")

  customized-badge as described in §7.3.
- **Logger** — view + clear the persisted ring buffer (RPC reads the
  entire buffer — it's bounded, so pagination isn't needed). Toggles for
  `enabled` and `logPayloads`. Filter by level + tag in-browser.
- **Backup** — Export (with export-password prompt + a download button)
  and Import (file picker, password prompt, mode picker).

## 11. Logger

- Single ring buffer in the SW, persisted as an encrypted blob, capped
  at `LOG_RING_BUFFER_SIZE` (default 2000) entries.
- API: `log(level, tag, message, payload?)`. Microtask-batched flush so
  burst logging (RPC routing, LLM streaming) absorbs into a single write
  rather than thrashing storage.
- **Redaction**: any payload key matching `authorization`, `x-api-key`,
  `api[_-]?key`, `apikey`, `cookie`, `set-cookie`, `password`, or a
  substring `secret` / `token` is replaced with `'[REDACTED]'`. Recurses
  with a depth cap (≈6).
- Two flags in settings:
  - `enabled` — gate everything; if off, `log()` returns silently.
  - `logPayloads` — gate whether `payload` is persisted at all
    (redaction still applies as a backstop).
- Non-SW contexts (content script, side panel, options) route through a
  `log-event` RPC so everything lands in one buffer.
- The logger must **never throw**. Any failure (settings missing, vault
  locked, storage full) is silently dropped — logging is observation,
  not the program's main path.

## 12. Diagnostics

A `run-diagnostic` RPC the side panel can fire on demand. Returns:

- SW alive (implied by the response).
- Vault unlocked? (boolean)
- Embedding round-trip ok? (boolean + dims + elapsed ms, or error string)
- Port snapshot: number of side-panel ports, content ports per tab,
  content ports for the active tab.
- LLM presence-check: `activeBackend`, `hasApiKey` (boolean — never the
  key itself), `model`. **Don't make a real API call** — diagnostics
  shouldn't burn user tokens; the presence check catches the most common
  misconfig (forgot to paste the key).

The whole result must be safe to copy-paste into a bug report. No secrets
inside.

## 16. Testing

The test pyramid for this extension:

- **Unit tests (vitest).** Cover everything that's pure logic and lives in
  the SW: messaging schemas (round-trip encode/decode + zod validation),
  the label-cleaning helper, fuse.js threshold behavior, RAG scoring +
  token-budgeted greedy packer, the dedup decision (matrix of
  `qSim × gSim` vs. thresholds, including the embedding-dim mismatch
  short-circuit), the merge-undo restoration, AES-GCM round-trips with
  wrong-password / tampered-IV cases, the backup envelope reader for every
  declared error kind, and the JSON-extraction helper on assorted real
  model outputs. LLM adapters are tested against fixture streams (recorded
  SSE / JSONL bodies) — never live network.
- **Component tests (Svelte component testing).** State transitions for
  `App.svelte` (loading / setup / locked / unlocked), `DraftArea.svelte`
  edit-mode toggling and partial-stream rendering, `ApplicationSetup.svelte`
  validation, and the toast components.
- **End-to-end (Playwright with the extension loaded).** The acceptance
  criteria in §17 are the canonical E2E suite. Run against a stub LLM
  endpoint that yields deterministic streamed bytes (so test runs don't
  cost money and don't depend on the network). Cover at minimum: the
  Alt+A → profile hit path, the Alt+A → classifier → story_answer happy
  path, Esc cancellation at every state, the manual-highlight fallback,
  Alt+S add-to-profile, and the export → import round-trip with both
  modes.
- **Manual smoke list.** Anything DOM-shape-sensitive — Workday, Greenhouse,
  Lever, Ashby, Microsoft Forms — gets a manual pass before each release.
  Maintain a short living document of "sites known to work" in the repo.

## 17. Acceptance checklist

A developer can consider the implementation done when:

- [ ] Pressing Alt+A on a form field opens the side panel (if not open),
      runs the detective, and shows the resolved label in the status
      ticker — without any prior auto-detection.
- [ ] If the detective fails, the side panel asks the user to highlight
      the question and press Enter; if `currentValue` is empty for an
      Alt+S press, the SW refuses with a status message instead of saving.
- [ ] Disabled / readonly / `<input type="file">` fields surface "This
      field can't be filled" and end the session.
- [ ] A direct profile match (fuse.js against `aliasMap` at
      `settings.matching.fuseThreshold`) shows the proposed value immediately
      as a field value AND in the side panel; pressing Enter commits via
      the native setter and dispatches `input` + `change` events.
- [ ] For `select` / `radio` / `checkbox` profile hits, fuse.js picks the
      best option; on miss, the `chooser` prompt runs; on `"No good options"`
      the flow falls through to the classifier as if no match existed.
- [ ] When no profile match exists, the SW runs the classifier prompt and
      branches into one of three flows (`profile_existing_value`,
      `profile_update`, `story_answer`).
- [ ] The `story_answer` flow prompts for company / role / blurb if no
      `ActiveApplication` is set; on submit, derives the `genericKey` via
      the `generic_key` prompt and embeds it; the result is cached in
      `chrome.storage.session` and re-used until the user clears it.
- [ ] Answer streaming flows tokens to the side panel draft area (with caret).
- [ ] Mid-stream LLM failures keep partial tokens visible, surface in
      `ErrorBanner.svelte`, expose Retry only when `retryable === true`,
      and never auto-retry.
- [ ] Esc anywhere from Alt+A through commit aborts: stream cancelled,
      panel cleared, status: "Cancelled".
- [ ] Approve commits via the native setter and dispatches input/change.
- [ ] On commit, dedup runs over history skipping entries whose embedding
      length doesn't match the current model's dimension; merges keep
      `id` + `createdAt`, overwrite the rest, and show a "merged into
      older, more general answer — keep older?" toast for 10s.
- [ ] Clicking Undo on the merge toast restores every overwritten field
      on the older entry; the form field is not touched; the new answer
      is discarded from history (not stored as a separate entry).
- [ ] If the user **edited** the LLM draft before approving, story
      discovery runs (fire-and-forget); a story-discovered toast shows
      proposed content + keywords; accept appends the new story to the
      story list. If the user did not edit the draft, story discovery is
      skipped entirely.
- [ ] add-to-profile (Alt+S): cleaned label fuse-matches an alias →
      append to the matched canonical key (deduped, case-insensitive);
      no match → create a new canonical key from the cleaned label and
      add the identity entry to `aliasMap`. A confirmation card appears
      when label > 50 chars or value > 100 chars, with editable key /
      value and a sensitive checkbox.
- [ ] Backup export produces an encrypted file with envelope
      `format: 'backup/v1'`; import restores it with both modes; wrong
      password and a tampered envelope both surface the same single
      "wrong password" message; every other error kind is surfaced
      distinctly per §8.3.
- [ ] All four LLM backends stream tokens for `story_answer_prompt`; the
      active backend is switchable on the Models page; Ollama shows the
      `OLLAMA_ORIGINS` command pre-filled with the actual extension id.
- [ ] Every prompt template is editable in Options → Prompts with a
      reset-to-default button, a `{{snake_case}}` cheat-sheet, and a
      "customized" badge when overridden.
- [ ] Every numeric `Settings` knob (matching / RAG / dedup) is editable
      from Options → General → Advanced thresholds, with each input
      printing its default and a per-knob reset button.
- [ ] Logger persists a redacted ring buffer; the Logger page renders it
      with toggles for `enabled` and `logPayloads`; the redaction list
      from §11 is exhaustive on the test fixtures.
- [ ] Vault locks on browser close (DEK lives in `chrome.storage.session`);
      password unlock and recovery-phrase unlock both work; both forgotten
      means data is unrecoverable (verified by attempting an unwrap with
      neither secret).
- [ ] Sensitive profile values (`profile.sensitiveKeys`) are excluded
      from `profile` for cloud-LLM prompts by default; the side
      panel surfaces "Some profile fields hidden from the LLM" so the
      user knows.
- [ ] Resume upload accepts `.docx` and `.txt` only; the onboarding
      screen tells the user PDFs are unsupported; extraction runs in the
      onboarding page; only the extracted text crosses the
      `parse-resume` RPC boundary.
- [ ] `run-diagnostic` returns SW-alive, vault-state, embedding
      round-trip, port snapshot, and an LLM presence-check that does not
      hit the network; the result has no secrets.
- [ ] One-shot LLM call failures (classifier, chooser, generic_key,
      answer_length) surface the error in `ErrorBanner.svelte` with a
      Retry button; the session is paused, not aborted; Cancel / Esc still
      aborts normally.
- [ ] Pressing Esc while focused inside the side panel (e.g., draft
      textarea) aborts the session identically to pressing Esc on the page
      — stream cancelled, panel cleared, status: "Cancelled".
